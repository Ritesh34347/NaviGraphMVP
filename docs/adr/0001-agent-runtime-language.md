# ADR 0001: Agent Runtime Language and Framework

## Status

Accepted — 2026-07-28. **Partially superseded — 2026-07-31**: the
LangGraph portion of this decision was explicitly reversed in Phase 9
after 8 phases and ~22 agents shipped with zero real need for graph
checkpointing/resumability ever emerging. The Request Orchestrator
(`orchestrator.request_orchestrator`) is a plain Python async function,
not a LangGraph graph — see `DECISIONS.md`'s 2026-07-31 "No LangGraph"
entry for the full reversal rationale. Every other part of this ADR
(Python 3.12, FastAPI, Pydantic v2) still stands as originally decided;
this note is deliberately additive, not a rewrite of the original
reasoning below, which remains accurate for why Python was chosen at all.

## Context

NaviGraph's agent runtime hosts an eventual ~25 agents (see
`docs/architecture/overview.md`) organized into six domains
(Understanding, Query, Guardrail, Ops, Insight, Orchestrator), coordinated as
a graph of LLM-backed and deterministic steps. We need to choose the
implementation language and core framework for this runtime
(`packages/agent_runtime`).

The main options considered were:

1. **Python** (FastAPI + Pydantic v2 + LangGraph) — the ecosystem most
   LLM-orchestration tooling, data/schema libraries, and warehouse client
   libraries (Snowflake, Trino) are written for or have first-class support in.
2. **TypeScript**, end-to-end — matching the `web/` Next.js frontend for a
   single-language stack across the whole product.

Key requirements driving the decision:

- A graph-of-agents orchestration model that matches our multi-domain,
  multi-agent architecture, including conditional routing and clarification
  loops.
- Strict, fast input/output validation matching the formal `AgentInput`/
  `AgentOutput` contract (`docs/architecture/agent-contract.md`).
- Mature client libraries for Snowflake, Trino, Neo4j, and the Anthropic API.
- Ability to expose each agent both as an in-process call and as a thin HTTP
  endpoint for isolated testing/eval, per the agent contract's dual-invocation
  requirement.

## Decision

We will build the agent runtime in **Python 3.12**, using **FastAPI** for the
HTTP layer, **Pydantic v2** for all `AgentInput`/`AgentOutput` contract models,
and **LangGraph** for orchestration of the agent graph.

## Consequences

- The agent runtime and the web UI are in different languages, so there is no
  shared type definitions between them at the source level; the contract
  boundary is the HTTP/JSON API (and its OpenAPI schema, generated by FastAPI)
  rather than shared TypeScript types.
- We gain access to the most mature LLM-orchestration ecosystem (LangGraph and
  its surrounding tooling) and the most mature data-engineering client
  libraries (Snowflake connector, Trino client, Neo4j driver) without needing
  to wait for or build TypeScript equivalents.
- Contributors need working Python knowledge to add or modify agents; this is
  an acceptable tradeoff since agent logic — the core intellectual property of
  the product — is the part of the codebase most engineers will spend time in.
- Pydantic v2's validation gives us a natural, low-overhead place to enforce
  the non-optional `RequestContext` requirement and the non-empty
  `lineage_events` requirement from the agent contract at the type level.
- This decision does not affect the choice of language for `packages/gateway`
  (also Python/FastAPI, for consistency with the agent runtime it proxies to)
  or `web/` (Next.js/TypeScript, see `DECISIONS.md`).
